Building a full site with FSCSS modules

One project, five modules, every import explained. This walks through building a real multi-section site — marketing page, dashboard, and a settings panel — by combining customizable, st-core, circle-progress, form, and cube. Each step covers exactly what you import, what it builds in the DOM, what it's good for, and what version of FSCSS it needs.

00 · What you're building

A creator dashboard, not five isolated demos

The example running through this tutorial is a small internal tool for DevTemple-style creators: a page that shows earnings over time, tracks progress toward a payout threshold, lets a creator request a withdrawal, and shows a small 3D badge when they hit a milestone. It's deliberately ordinary — the point isn't the dashboard, it's that five separately-maintained CSS modules sit on one page without fighting each other.

Every module in this ecosystem follows the same rule: it reads design tokens from its own @*-root mixin, renders its shapes with plain CSS (clip-path, gradients, transforms, pseudo-elements), and — where JavaScript shows up at all — only ever writes a CSS custom property. That rule is what makes combining them straightforward instead of a specificity fight.

Every code block below is copy-paste real — pulled from each module's actual mixin names and import syntax. The screenshots are reference images from each module's own write-up.

01 · Setup

Two ways to bring FSCSS in

Pick one depending on where you are in the build. Both compile the same shorthand to the same output — the only difference is when compilation happens.

Option A — CDN runtime (fastest to start)

Good for prototyping, demos, and this tutorial. The runtime script compiles any @fscss-flavored <style> block in the browser as the page loads.

html
<script src="https://cdn.jsdelivr.net/npm/fscss@1.1.24/exec.min.js" defer></script>

Option B — CLI, compiled ahead of time (production)

No runtime request, no in-browser compile step. This is what you switch to once the site is ready to ship.

bash
# once, globally
npm install -g fscss

# compile a source file to plain CSS
fscss site.fscss dist/site.css
Runtime weight
~10kb (CDN mode)
Compiled weight
~0.5kb / module
Minimum FSCSS
v1.1.24+
02 · Project structure

How a real FSCSS site is laid out

There's no bundler and no framework, so the structure stays close to the output. One source .fscss file per page (or one shared file plus page-specific ones), compiled into a matching .css file that ships to the browser.

creator-studio/
├── index.html                ← marketing / landing page
├── dashboard.html             ← the combined build in this tutorial
├── package.json
├── src/
│   ├── shell.fscss            ← customizable: nav, container, tokens
│   ├── dashboard.fscss        ← st-core + circle-progress + form + cube
│   └── tokens.fscss           ← shared $variables, brand overrides
├── dist/
│   ├── shell.css              ← compiled output, committed or built in CI
│   └── dashboard.css
└── assets/
    └── images/

Two working patterns, both fine:

  • Split by concern (shown above) — one .fscss file per structural layer, each compiled to its own .css. Easiest to reason about when different modules change at different rates.
  • One file per page — a single page.fscss that imports everything that page needs and compiles to one page.css. Simplest for smaller sites like this hub.
03 · The import system

What @import actually does here

FSCSS imports are selection-based, not file-based — you name which mixins you want out of a module, and only those get compiled into your output. This is the mechanism that keeps the ~0.5kb-per-module compiled weight honest: an unused mixin never ships.

Selective import — name exactly what you use

@import((page-hero, page-btn, page-btn-primary) from customizable)

Only page-hero, page-btn, and page-btn-primary compile. The module's footer, 404, and feature-grid mixins never enter your CSS, even though they live in the same source file.

Wildcard import — pull in everything

@import((*) from st-core)

Use this while you're still deciding which pieces of a module you need — during the first pass of a build, or for a module like st-core where a dashboard typically ends up using most of it anyway.

Multiple imports, one file

@import((*) from st-core)
@import((*) from circle-progress)
@import((form-root, form-group, form-float) from form)

Imports stack. Order rarely matters between different modules since each one's mixins are namespaced to its own prefix (@st-*, @form-*, @page-*, @cube-*, @progress-*) — no collisions between modules that were built independently.

Rule of thumb used throughout this tutorial: wildcard-import a module the first time you reach for it, then go back and narrow to a selective import once the page is stable and you know exactly which mixins survived.

Step 1 of 5 — customizable.fscss

Lay down the page shell

Every other module in this build inherits its spacing, radius, and color from whatever page-root writes to :root. Setting the shell first means the dashboard, the form, and the badge all line up without individually-tuned margins.

What it imports

dashboard.fscss
@import((page-root, page-base, page-hero,
         page-btn, page-btn-primary) from customizable)

@page-root()
@page-base(body)

What that structurally sets up

  • page-root writes the token layer — --page-accent, --page-radius, spacing scale — once, to :root. Every downstream module's own tokens can reference or be overridden alongside these.
  • page-base applies base typography and background to whatever selector you pass it — normally body.
  • page-hero and the button mixins are pulled in for the marketing landing page (index.html) that sits in front of the dashboard — not strictly required on the dashboard page itself, but sharing one shell.fscss keeps both pages visually identical.

What it's good for

Any page that needs consistent nav, spacing, and a button system without redefining them per page — landing pages, 404s, long-form content, and as the outer shell for pages that also use other modules, like this dashboard.

Overriding the brand

@page-root()

:root {
  --page-accent: #8f6bff;
  --page-radius: 14px;
}

Two lines here change the accent and radius everywhere customizable's mixins are used on the page.

Requires
FSCSS v1.1.24+
Breakpoint
640px, built-in

Step 2 of 5 — st-core.fscss

Render the earnings chart and stat card

The chart's data lives entirely in CSS custom properties (--st-p1 through --st-p8), and its shape is a clip-path: polygon() that reads them. Whatever your backend returns for "earnings this week" turns into eight numbers written to those variables — nothing else changes.

What it imports

dashboard.fscss
@import((*) from st-core)

@st-root()
@st-stat-card(.stat-card)
@st-chart-fill(.chart-fill)
@st-chart-line(.chart-line)
@st-chart-dots(.chart-dot-, 7px)
@st-chart-grid(.chart-grid, 8, 7)
@st-chart-axis-x(.x-axis)

Markup this generates behavior for

<div class="stat-card">
  <div class="st-stat-label">Earnings this week</div>
  <div class="st-stat-value">$2,140</div>
  <div class="st-stat-delta up">▲ +8.2%</div>
</div>

<div class="chart" style="position:relative;height:200px">
  <div class="chart-fill"></div>
  <div class="chart-line"></div>
  <div class="chart-dot-1"></div> <!-- through chart-dot-8 -->
  <div class="chart-grid"></div>
</div>

Feeding it real data

js
// the only JS this module needs — write the variable, CSS repaints
function setChartData(el, values) {
  values.forEach((v, i) => {
    el.style.setProperty(`--st-p${i + 1}`, (100 - v) + '%');
  });
}
setChartData(document.querySelector('.chart'), [20, 35, 40, 55, 48, 72, 60, 80]);

What it's good for

Any dashboard-style view that needs a line chart, area fill, or stat card without pulling in a charting library — earnings graphs, activity trends, category breakdowns. It's not a substitute for a full charting library when you need tooltips-on-every-point, zoom, or export; it's built for the common "show a trend, glanceable, fast" case.

Requires
FSCSS v1.1.24+
Rendering
clip-path polygons

Step 3 of 5 — circle-progress.fscss

Track progress toward the payout threshold

The color logic lives inside FSCSS itself, not in your JavaScript. An @event function maps a percentage to a color, and an @arr loop pre-generates every state from .p-0 to .p-99 at compile time. Your JS only ever swaps a class name.

What it imports

dashboard.fscss
@import((*) from circle-progress)

@progress-root()
@circle-progress(#progress[class^='p-'])
@progress-animate(2s)

The color logic, defined once

@event range-color(range){
    if range <= 30 { return: #D69308 }
    el-if range <= 60 { return: #86CA1A }
    el-if range <= 95 { return: #13B046 }
    el { return: #26FF00 }
}

Generating every percentage state

@arr p-ranges[count(100)]
.p-@arr.p-ranges[]{
    $range: @arr.p-ranges[];
    @progress-range($range)
    --progress-color-arc: @event.range-color($range);
}

JavaScript — one line, on input

js
const progress = document.getElementById('progress');
function setPayoutProgress(percent) {
  progress.className = `p-${Math.min(Math.round(percent), 100)}`;
  progress.textContent = `${percent}%`;
}
setPayoutProgress(68); // 68% of the way to the next payout tier

What it's good for

Any single-value goal indicator where the color should mean something — storage quotas, onboarding completion, a payout tier, a battery-style health score. Less suited to a value that needs to show multiple segments at once (use st-core's category bars for that instead).

Requires
FSCSS v1.1.24+
JS role
writes 1 class name

Step 4 of 5 — form.fscss

Build the withdrawal request form

Floating labels run entirely on :placeholder-shown — give the input a literal space as its placeholder and the browser already knows, in pure CSS, whether the field is empty and unfocused. Checkboxes and the toggle switch reuse the classic checkbox-hack, so the real input stays keyboard- and form-submit-native.

What it imports

dashboard.fscss
@import((form-root, form-group, form-input, form-label,
         form-float, form-help, form-validation, form-select,
         form-select-arrow, form-btn, form-btn-primary) from form)

@form-root()
@form-group(.form-group)
@form-input(.form-input)
@form-label(.form-label)
@form-float(.form-group, .form-input, .form-label)
@form-validation(.form-group)
@form-btn(.form-btn)
@form-btn-primary(.form-btn-primary)

The markup — note the input-before-label order

<div class="form-group is-success">
  <input class="form-input" type="number" placeholder=" ">
  <label class="form-label">Withdrawal amount</label>
  <span class="form-help">Available: $2,140</span>
</div>

<button class="form-btn form-btn-primary" style="width:100%">Request withdrawal</button>

Two rules that make it work

  • The placeholder must be a literal space (placeholder=" "), not an empty string — that's what :placeholder-shown checks against.
  • The <input> must come before the <label> in markup order, because the floating-label rule uses a sibling selector (+) that only looks forward.

What it's good for

Any form where the visual states — resting, focused, filled, valid, invalid — should react automatically instead of being toggled by JavaScript on every keystroke. Your own validation logic (an async check, a regex) still needs real code; this module only owns how the result of that check looks.

Requires
FSCSS v1.1.24+
JS needed
0, for visual states
Source
fscss-ttr/form.fscss
Step 5 of 5 — cube.fscss

Add the milestone badge

A small, real 3D cube — six absolutely-positioned faces on a preserve-3d parent — that appears once a creator crosses a milestone. It's the smallest piece of this build on purpose: a detail that rewards a threshold, not the centerpiece of the page.

What it imports

dashboard.fscss
@import((cube-root, cube-wrapper, cube-face, cube-face-front,
         cube-face-back, cube-face-left, cube-face-right,
         cube-face-top, cube-face-bottom, cube-micro-glass) from cube)

@cube-root()
@cube-wrapper(.milestone-badge)
@cube-face(.milestone-badge div)
@cube-face-front(.milestone-badge .f1)
@cube-face-back(.milestone-badge .f2)
@cube-face-left(.milestone-badge .f3)
@cube-face-right(.milestone-badge .f4)
@cube-face-top(.milestone-badge .f5)
@cube-face-bottom(.milestone-badge .f6)
@cube-micro-glass(.milestone-badge .f1)

.milestone-badge {
  @cube-size(48px)
  transform: rotateY(30deg) rotateX(15deg);
  animation: badge-spin 6s linear infinite;
}

@keyframes badge-spin {
  0%   { transform: rotateX(15deg) rotateY(30deg); }
  100% { transform: rotateX(375deg) rotateY(390deg); }
}

What it's good for

Small decorative or state-signaling 3D — an achievement badge, a spinning brand mark, a decision cube. The face and face-content mixins are decoupled on purpose, so the same six-face geometry works for a dice roll, a rotating logo, or a badge like this one, just by swapping which "micro" effect sits on each face.

Because it's the smallest visual footprint of the five modules here, this is also the easiest one to cut if the page is running heavy — nothing else on the dashboard depends on it.

Requires
FSCSS v1.1.24+
Geometry
real 3D, preserve-3d
Micro effects
8 available
Putting it together

The full assembled dashboard.fscss

Every import from the five steps above, stacked in one file. This is what actually ships — either loaded live via the CDN runtime while you're building, or compiled once with the CLI for production.

src/dashboard.fscss
/* shell */
@import((page-root, page-base) from customizable)
@page-root()
@page-base(body)

/* charts + stats */
@import((*) from st-core)
@st-root()
@st-stat-card(.stat-card)
@st-chart-fill(.chart-fill)
@st-chart-line(.chart-line)
@st-chart-dots(.chart-dot-, 7px)
@st-chart-grid(.chart-grid, 8, 7)

/* payout goal ring */
@import((*) from circle-progress)
@progress-root()
@circle-progress(#progress[class^='p-'])

/* withdrawal form */
@import((form-root, form-group, form-input, form-label,
         form-float, form-help, form-btn, form-btn-primary) from form)
@form-root()
@form-group(.form-group)
@form-input(.form-input)
@form-label(.form-label)
@form-float(.form-group, .form-input, .form-label)
@form-btn(.form-btn)
@form-btn-primary(.form-btn-primary)

/* milestone badge */
@import((cube-root, cube-wrapper, cube-face-front,
         cube-micro-glass) from cube)
@cube-root()
@cube-wrapper(.milestone-badge)
@cube-face-front(.milestone-badge .f1)
@cube-micro-glass(.milestone-badge .f1)

/* brand override — cascades to every module above */
:root {
  --page-accent: #8f6bff;
  --st-accent:   #8f6bff;
}

Note the brand override at the bottom: because every module reads its accent from its own CSS custom property, one small block at the end of the file re-themes the chart, the stat card, and the page shell together — the same pattern customizable.fscss uses on its own.

Going to production

Compile once, ship plain CSS

Once the dashboard looks right under the CDN runtime, swap it for a compiled build — same source, no runtime dependency in production.

bash
fscss src/dashboard.fscss dist/dashboard.css

Then swap the CDN <script> for a plain stylesheet link:

<!-- before, while building -->
<script src="https://cdn.jsdelivr.net/npm/fscss@1.1.24/exec.min.js" defer></script>
<style>@import((*) from st-core) ...</style>

<!-- after, in production -->
<link rel="stylesheet" href="dist/dashboard.css">

If the source files change often, wire the compile step into CI so dist/*.css stays in sync automatically — a workflow that watches for changes to **.fscss, runs the FSCSS CLI, and commits or deploys the result. That pattern (compile-on-push, deploy the compiled output) is documented in the ecosystem's own CI write-up if you want the exact GitHub Actions setup.
